## 0. Що змінилося порівняно з v0.4

| Тема | v0.4 | v0.5 |
|---|---|---|
| Оцінка сектора | Лише слайдер 0–10 | Слайдер 0–10 лишається **остаточною** оцінкою. Додано **необов'язковий** опитувальник критеріїв і орієнтир, обчислений з відповідей |

| Наставники | Відкладено | Як і раніше, відкладено. Модель критеріїв уже має `origin`/`status`/`author`, тож наставницькі критерії додаються без міграції історії |
| Каталог | — | 160 критеріїв як файл імпорту `criteria.v1.yml` зі стабільними ключами. 7 формулювань зроблено гендерно-нейтральними (див. 9.4) |
| Roadmap | 11 кроків | 14 кроків (додано критерії, опитувальник, entitlement) |

## 1. Executive summary

**Концепція v0.4 додає цінну річ:** критерії розв'язують головну проблему шкали 0–10, бо без орієнтирів сьогоднішня «6» і завтрашня «6» означають різне. Підхід «орієнтир + незалежна остаточна оцінка користувача» правильний, і його варто зберегти.

**Що зберегти:**
- Усе з v0.4: 8 секторів, незмінні зрізи, чернетку, приватність за замовчуванням, соцлогін через contrib.
- Остаточна оцінка ставиться **людиною**, а формула лише підказує.
- «Так / Частково / Ні / Не стосується», де відсутність відповіді є окремим станом.
- Безкоштовне ядро; дані користувача ніколи не ховаються за paywall.

**Що спростити або виправити:**

| Пропозиція v0.4 | Рекомендація | Чому |
|---|---|---|
| Окрема сутність `AssessmentResponse` | **Поле `answers` у зрізі** (multi-value: criterion_id, criterion_revision_id, answer) | Відповіді успадковують access control зрізу автоматично, тож друга сутність не стає ще одним місцем для витоку. Зріз = атомарний датований запис. |
| «Збалансованість підкатегорій» у формулі | **Не робити в MVP.** Підкатегорій у каталозі немає | Формула має бути пояснюваною одним реченням. Інакше це «надмірна точність», від якої концепція сама застерігає. |
| Premium з оплатою | **Premium у MVP = feature flag + ручна видача** (бета, члени ком'юніті). Оплата з'являється лише в 1.1, після вибору провайдера | Найдешевший стабільний шлях: без каси, але з правильною серверною перевіркою, яку потім просто «підживить» платіжний вебхук. |
| 160 запитань як «оцінювання» | Опитувальник **необов'язковий і посекторний**: можна пройти 1 сектор, а можна одразу рухати слайдер | 80 запитань — це приблизно 6–10 хв, 160 — 12–20 хв. Обов'язковий опитувальник вбиває повторні зрізи. |
| Наставницькі критерії в моделі | Лише поля `origin`, `status`, `uid` у сутності критерію. **Жодних ролей, форм і прав наставника в MVP** | Модель готова, функціональність відкладена. |

**Головні ризики** (з v0.4 + нові):
1. Автоматичне прив'язування акаунта за email у соцлогіні → account takeover. **[ПЕРЕВІРИТИ поведінку social_auth 4.x]**
2. Витік персональних сторінок через кеш.
3. **Нове: ілюзія точності.** Орієнтир «6.67» сприймається як діагноз. Тому показуємо ціле число, підпис «орієнтир», пояснення формули й можливість його ігнорувати.
4. **Нове: підміна формулювань заднім числом.** Якщо редагувати текст критерію на місці, історичні відповіді почнуть «відповідати» на інше питання. Розв'язок: ревізії плюс посилання відповіді на конкретну ревізію.
5. **Нове: несумісні порівняння.** Free-орієнтир (10 критеріїв) і Premium-орієнтир (20) не можна порівнювати як рівні. Розв'язок: порівнюємо остаточні оцінки завжди, а орієнтири лише за однакового режиму й версії формули.
6. **Нове: юридичне.** Premium зі справжньою оплатою вимагає оферти, політики повернень і податкової моделі. Це не входить у MVP.

## 2. Межі релізів

| Реліз | Що входить |
|---|---|
| **MVP 1.0** | Соцлогін (Google + Facebook), колесо, чернетка, зрізи з нотаткою, історія, порівняння, динаміка, експорт/видалення. **Free-критерії (80)** як необов'язковий посекторний опитувальник з орієнтиром. Адмін-інтерфейс системних критеріїв. **Premium-критерії (80)** імпортовані, але доступні лише за `EntitlementChecker` (flag `premium_enabled`, видача вручну адміністратором). Без оплати. |
| **1.1** | Інтеграція платіжного провайдера (hosted checkout + вебхуки → entitlement), сторінка тарифу, неагресивна пропозиція Premium. Рекомендації/цілі/чеклісти (окремий модуль). Нагадування. |
| **1.2** | Наставники: пропозиції критеріїв у каталог із модерацією, персональні критерії за згодою, точкові дозволи на перегляд. |
| **2.0+** | Групи, програми, AI (з окремою згодою), власні сектори, кілька коліс. |

**Чіткий поділ понять** (вимога 11.4):
- **Критерій самооцінювання** — твердження, на яке людина відповідає, щоб краще оцінити сектор. Входить у MVP, сутність `lifebalance_criterion`.
- **Рекомендація / ціль / чекліст** — дія, яку людина планує виконати. Це 1.1, окремий модуль, окремі сутності. Виконання дій **ніколи** не змінює ні відповіді на критерії, ні оцінку.

## 3. Edge cases і неоднозначності

| # | Ситуація | Рішення |
|---|---|---|
| E1 | Зріз без усіх оцінок | Заборонено. Зберегти можна лише тоді, коли всі активні сектори мають остаточну оцінку 0–10. `NULL` допускається лише в чернетці. |
| E2 | 0 проти «не оцінено» | `0` — валідна оцінка, `NULL` — не оцінено. Окремий UI-стан. |
| E3 | Кілька зрізів на день | Дозволено з м'яким попередженням. Сортування `created DESC, id DESC`. |
| E4 | Помилковий зріз | Оцінки й відповіді не редагуються, зріз можна видалити, нотатку можна редагувати. |
| E5 | Таймзони | UTC у БД, відображення в таймзоні профілю (за замовчуванням Europe/Kyiv). |
| E6 | 0 / 1 / 2+ зрізів | Окремі пояснювальні стани. Порівняння доступне з 2 зрізів. |
| E7 | Обмеження частоти | Не більше 50 зрізів на добу, draft API не більше 120 запитів на хвилину на користувача. |
| E8 | Чернетка у двох вкладках | Last-write-wins. |
| E9 | Видалення акаунта | Каскад: зрізи (з відповідями), чернетка, social_auth, entitlement. |
| E10 | Провайдер не дав email | Вхід дозволено, але попереджаємо, що без email відновлення неможливе. **[ПЕРЕВІРИТИ обробку в social_auth]** |
| **E11** | Користувач відповів на критерії, але не рухав слайдер | Слайдер **не заповнюється автоматично**. Біля нього з'являється кнопка «Взяти орієнтир (7)», і бал переноситься лише тоді, коли користувач її натисне. Так остаточна оцінка лишається свідомою дією людини. |
| **E12** | Орієнтир і остаточна оцінка сильно розходяться | Це нормально. Можна показати нейтральний текст «Ваша оцінка відрізняється від орієнтиру — це нормально, орієнтир лише підказка». Без попереджень і червоних кольорів. |
| **E13** | Відповіді на частину критеріїв сектора | Орієнтир рахується лише тоді, коли є не менше 5 змістовних відповідей (Так/Частково/Ні) у Free-режимі або не менше 10 у Premium. Інакше показуємо «Замало відповідей для орієнтиру». |
| **E14** | Усі відповіді «Не стосується» | Орієнтира немає. |
| **E15** | Premium відкликано | Premium-відповіді в старих зрізах **лишаються видимими** власнику. Нові Premium-відповіді недоступні, а з чернетки вони прибираються. Сам режим зрізу не змінюється. |
| **E16** | Критерій архівовано або змінено текст | Старі зрізи показують ту ревізію, на яку відповідали. У новій чернетці відповідь на змінений критерій скидається з позначкою «формулювання оновлено». |
| **E17** | Незавершене опитування | Відповіді живуть у чернетці (автозбереження). Прогрес видно по секторах: «Здоров'я 7/10». |
| **E18** | Порівняння зрізів з різними режимами | Остаточні оцінки порівнюються завжди, але з бейджем режиму («базовий / розширений / без опитувальника»). Орієнтири порівнюються лише за однакового `assessment_mode` + `formula_version`, а відповіді — лише за однакової ревізії критерію. |

## 5. Модель даних

### 5.1. Альтернативи для критеріїв (вимога 11.4)

| Варіант | + | − | Вердикт |
|---|---|---|---|
| Config entity | Git/config sync, переклад через config translation | **Немає ревізій**, автора, модерації. Наставники в 1.2 не зможуть створювати критерії на проді без config deploy. Історичні формулювання не зберігаються. | ✗ |
| Node «Criterion» | Ревізії, автор, модерація з коробки | Node-access і Views роблять його «публічним за замовчуванням». Персональні критерії (1.2) стануть ризиком витоку. Багато зайвого (path, menu, promote) | ✗ |
| Taxonomy term | Порядок, ієрархія | Ревізії обмежені, семантика інша | ✗ |
| **Custom content entity `lifebalance_criterion`, revisionable** | Ревізії = незмінні історичні формулювання, автор, статус, власний access handler, розширення під наставників | Потрібен імпорт між середовищами (вирішується файлом даних + drush-командою) | **✓** |

### 5.2. `lifebalance_sector` (config entity)

Без змін з v0.4: `id` (незмінний, ≤32), `label`, `description`, `weight`, `color`, `status`. Видалити не можна, можна лише вимкнути.

### 5.3. `lifebalance_criterion` (content entity, revisionable, не translatable у MVP)

| Field | Тип | Примітки |
|---|---|---|
| `id`, `uuid`, `revision_id` | — | — |
| `key` | string(64), **unique** | Стабільний ключ `health.f01`. Не змінюється. Сюди ж підуть майбутні `mentor.<uuid>` |
| `sector` | string(32) | ID сектора, індекс |
| `tier` | list: `free` / `premium` | — |
| `text` | string(255), **revisionable** | Формулювання. Будь-яка зміна тексту **примусово** створює нову ревізію (`preSave`) |
| `help` | string_long, revisionable, nullable | Пояснення до твердження (необов'язково) |
| `weight` | int | Порядок у секторі |
| `status` | list: `draft` / `published` / `archived` | В опитувальнику лише `published` |
| `origin` | list: `system` (MVP); `mentor_proposed`, `personal` додадуться в 1.2 | Готовність до наставників без зміни схеми історії |
| `in_formula` | bool, default TRUE для system | Критерії наставників (1.2) за замовчуванням FALSE, як вимагає 11.2 |
| `uid` | entity_reference → user | Автор (адмін у MVP) |
| `changed` | timestamp | — |

Обмеження: ревізії критеріїв **не видаляються** (access deny на revision delete). Критерій, на який є відповіді, не можна видалити, лише архівувати.

Індекс `(sector, tier, status, weight)`.

### 5.4. `lifebalance_snapshot` (content entity, не revisionable)

| Field | Тип | Примітки |
|---|---|---|
| `id`, `uuid` | — | UUID використовується в URL |
| `uid` | entity_reference → user | Індекс `(uid, created)` |
| `created` | timestamp UTC | — |
| `note` | string_long ≤1000 | Приватна |
| `assessment_mode` | list: `none` / `free` / `premium` | Найвищий режим, у якому були відповіді в цьому зрізі |
| `formula_version` | string(16), nullable | Наприклад `v1`. Задається, лише якщо є хоча б один орієнтир |
| `scores` | field type `lifebalance_score`, unlimited | `sector_id` varchar(64), `value` tinyint 0–10 (**остаточна**, NOT NULL), `guide` smallint nullable (орієнтир ×10, тобто 0–100), `answered` tinyint (кількість змістовних відповідей) |
| `answers` | field type `lifebalance_answer`, unlimited | `criterion_id` int, `criterion_revision_id` int, `answer` enum `yes` / `partial` / `no` / `na`. Немає відповіді = немає рядка. Індекс `criterion_id` |

Чому `answers` є полем, а не окремою сутністю: зріз створюється й видаляється атомарно, access control один, експорт і видалення простіші. Обсяг до 160 рядків на зріз; для сотень зрізів на користувача це дрібниця.

Валідація зрізу:
- кожен активний сектор має `value`;
- `answers` посилаються на `published` критерії на момент збереження;
- `criterion_revision_id` = поточна ревізія;
- Premium-відповіді дозволені лише за `EntitlementChecker::hasPremium()`;
- `guide` **перераховується на сервері**, значенню з клієнта не довіряємо.

### 5.5. Чернетка

`user.data` (`lifebalance` / `draft`):
```
{ scores: {sector_id: int|null}, answers: {criterion_id: {rev: int, a: "yes"|"partial"|"no"|"na"}}, updated: ts }
```
Ліміт тіла запиту 16 KB (160 відповідей поміщаються).

### 5.6. Premium / entitlement

- **MVP:** сервіс `EntitlementChecker::hasPremium(AccountInterface): bool` з кеш-контекстом `user`.
  - Реалізація: `config lifebalance.settings:premium_enabled` && (користувач має permission `use premium criteria`).
  - Permission видається ролі `premium_member`, яку адмін присвоює вручну (бета-тестери, учасники ком'юніті).
  - Коли `premium_enabled = FALSE`, Premium-критерії не показуються взагалі, і пропозиції теж немає.
- **1.1:** бекенд сервісу перемикається на content entity `lifebalance_entitlement` (uid, product, source=`provider`, provider_ref, status `active` / `revoked` / `refunded`, starts, expires). Вебхуки провайдера створюють і відкликають записи. Сигнатура вебхука перевіряється, обробка ідемпотентна за `provider_event_id`. Карткових даних у Drupal немає: лише hosted checkout і мінімальний `provider_ref`. **Інтерфейс сервісу не змінюється**, тому контролери й форми з MVP працюють без змін.
- **Ніде в коді** не перевіряти ролі напряму, лише `EntitlementChecker`.

### 5.7. Окремої сутності `BalanceWheel` немає

Причини ті самі, що й у v0.4.

## 6. Модуль і структура

Один модуль `lifebalance` + тема `lifebalance_theme`. Критерії природно лягають у той самий домен. Окремий модуль `lifebalance_billing` з'явиться в 1.1 разом з оплатою, а `lifebalance_plans` (рекомендації й цілі) теж у 1.1.

```
lifebalance/
  config/install/        сектори, lifebalance.settings (premium_enabled: false, formula_version: v1)
  config/schema/
  data/criteria.v1.yml   каталог 160 критеріїв (вже підготовлено)
  src/Entity/            Sector, Criterion, Snapshot
  src/Plugin/Field/FieldType/   ScoreItem, AnswerItem
  src/Plugin/Validation/Constraint/
  src/Access/            SnapshotAccessControlHandler, CriterionAccessControlHandler
  src/Service/           SectorRepository, CriterionRepository, SnapshotRepository,
                         DraftStorage, GuideCalculator, EntitlementChecker, LifeBalanceAccess
```

## 8. Історична коректність

**Сектори:** ID незмінні. Перейменування змінює лише label. Зміна сенсу означає новий ID і вимкнення старого (див. v0.4).

**Критерії:**
1. `key` незмінний.
2. Будь-яка зміна `text` створює нову ревізію (примусово, не за галочкою).
3. Відповідь зберігає `criterion_revision_id`, і перегляд старого зрізу показує саме ту ревізію.
4. Видалення критеріїв і ревізій заборонене, є лише `archived`.
5. Суттєва зміна змісту (а не правка коми) оформлюється як новий `key` і архівування старого. Редакційне правило: «якщо відповідь людини на старе й нове формулювання могла б відрізнятися, то це новий key».
6. Імпорт `criteria.vN.yml` ідемпотентний: новий key створює критерій, змінений text створює нову ревізію, відсутній у файлі key **не видаляється** (лише лог-попередження).

**Формула:** `formula_version` зберігається в зрізі. Якщо формула зміниться, старі орієнтири **не перераховуються** і порівнюються лише всередині своєї версії.

## 9. Критерії, формула, UX, Free/Premium

### 9.1. Чи потрібна автоматична формула в MVP?

**Так, але як «орієнтир», а не як оцінка.** Без числа людині складно перейти від відповідей до слайдера. З числом є ризик анкорингу, але він прийнятний, якщо:
- остаточну оцінку ставить людина (E11);
- формулу пояснено одним реченням на екрані;
- орієнтир показується **цілим числом**.

**Формула `v1`:**
- Так = 1, Частково = 0.5, Ні = 0. «Не стосується» й відсутність відповіді **не враховуються**.
- `guide = round(10 × сума / кількість_змістовних_відповідей)`, ціле 0–10. У БД зберігається ×10 для майбутньої точності.
- Мінімум змістовних відповідей: 5 (Free) / 10 (Premium).
- Режим `premium` рахує всі 20 критеріїв сектора разом, режим `free` — лише 10 базових.
- Пояснення в UI: «Орієнтир — частка тверджень, з якими ви погодились (частково = половина), переведена в шкалу 0–10».

Підкатегорії й ваги критеріїв **не робимо**: у каталозі їх немає, а складність формули створює хибну точність.

### 9.2. UX опитувальника

- Опитувальник **необов'язковий**. Головний шлях — слайдер. Посилання «Допомогти з оцінкою (10 тверджень)» є біля кожного сектора.
- Один сектор = один екран (`/wheel/{sector}`). Прогрес «4/10», кнопки «Назад до колеса» і «Наступний сектор».
- Кожне твердження оформлене як `fieldset` + `legend`, а 4 radio-кнопки (Так / Частково / Ні / Не стосується) великі й зручні для дотику. На мобільному вони стоять у ряд 2×2. Нічого не вибрано за замовчуванням.
- «Очистити відповідь» дозволяє повернути стан «без відповіді».
- Автозбереження відповідей у чернетку. Можна піти й повернутися.
- Після сектора показується підсумок: «Так: 6, Частково: 2, Ні: 1, Не стосується: 1 → орієнтир 7. Ваша оцінка: [слайдер] [Взяти орієнтир]».
- Орієнтовний час на екрані: Free близько 1 хв на сектор (6–10 хв усе), Premium додає ще 1 хв на сектор.
- Premium-блок з'являється **після** Free-блоку сектора, лише якщо є entitlement. Без entitlement і за `premium_enabled` показується один рядок: «Є ще 10 поглиблених тверджень у розширеному оцінюванні → Детальніше». Без модалок, таймерів і повторів частіше ніж раз на сесію. **Не показувати це до першого збереженого зрізу.**
- Повторне оцінювання: відповіді попереднього зрізу підставляються в чернетку як стартові (за тієї ж ревізії критерію). Так людина відповідає «що змінилось», а не все з нуля.

### 9.3. Free/Premium: серверні правила

- Премія відкриває **функцію** (доступ до Premium-критеріїв і режиму `premium`), а не окремі колеса чи окремих користувачів.
- Перевірка відбувається на сервері в трьох місцях: рендер форми, валідація зрізу/чернетки (Premium-відповіді без entitlement відкидаються з 403/помилкою валідації), access до `/wheel/{sector}`. Приховати кнопку недостатньо.
- Свої дані користувач бачить **завжди**, незалежно від статусу Premium (E15). Експорт включає всі відповіді.
- Відкликання: entitlement → revoked → нові Premium-відповіді недоступні, історія доступна.
- 1.1 (оплата, **не реалізовувати зараз**): hosted checkout, вебхук з перевіркою підпису, ідемпотентність, `refunded` → revoked, повторна покупка → новий entitlement запис (історія покупок), у БД лише `provider_ref` і статус, у privacy notice — розділ про платежі. Вирішити до 1.1: модель (разово / підписка), провайдер, оферта, повернення, податки.

## 11. Security & privacy checklist

**Доступ**
- [ ] Snapshot: view/update/delete лише власнику, без винятків для адміністраторів. `admin_permission` нікому не видається.
- [ ] Criterion: view `published` system-критеріїв для залогінених (тексти не секретні), але Premium-тексти показуються лише за entitlement. Адмін-операції через `administer lifebalance criteria`.
- [ ] `EntitlementChecker` — єдина точка перевірки Premium. Тест на обхід: POST чернетки/зрізу з Premium-відповіддю без entitlement → відхилено.
- [ ] Немає views_data, collection routes для зрізів; JSON:API/REST не ввімкнені.
- [ ] UUID замість ID в URL.
- [ ] Ролі: `site_manager` (критерії, сектори, видача `premium_member`) **не має** доступу до зрізів. uid 1 не використовувати щодня.

**Запити й кеш**
- [ ] Form API token / `_csrf_request_header_token`.
- [ ] Серверний перерахунок `guide`.
- [ ] Flood limits.
- [ ] `#cache contexts: user` для персональних даних, `Cache-Control: private, no-store`.
- [ ] Сторінки з Premium-критеріями мають cache context `user` (бо залежать від entitlement), а не лише `user.permissions`, оскільки бере участь ще й flag.

**Дані**
- [ ] Експорт: зрізи, оцінки, орієнтири, відповіді з текстом ревізії, нотатки, чернетка, статус Premium.
- [ ] Видалення: зрізи (поля відповідей видаляються разом), чернетка, social_auth, роль premium_member.
- [ ] Без оцінок, відповідей і нотаток у логах.
- [ ] Privacy notice: самооцінка не є діагностикою; хто має технічний доступ; бекапи; (1.1) платежі.
- [ ] Секрети лише в env/settings.local.php.

## 17. Рішення, які треба зафіксувати до Cursor

1. D11 latest, PHP за core, MariaDB, DDEV.
2. Один модуль `lifebalance` + тема.
3. Сутності: sector (config), criterion (content, revisionable), snapshot (content) з полями `scores` і `answers`. Чернетка в user.data.
4. Остаточну оцінку ставить людина. Орієнтир рахується за формулою v1, ціле число, мінімум 5/10 відповідей.
5. Опитувальник необов'язковий і посекторний.
6. Premium = `EntitlementChecker` + flag `premium_enabled` (за замовчуванням FALSE) + роль `premium_member`, без оплати.
7. Зрізи: видалення так, редагування ні, нотатка редагується. Кілька на день можна з попередженням.
8. Автолінк акаунтів вимкнено.
9. Form API + vanilla JS + SVG.
10. Каталог імпортується з `data/criteria.v1.yml`, зміна тексту створює ревізію.
